# Demo narration (word-for-word voiceover)

Read this aloud while you follow `DEMO_SCRIPT.md`. Bracketed `[actions]` are
what to do on screen — don't read them. Speak naturally; it's fine to paraphrase.
Target ~6 minutes.

---

## 0. Intro

"Hi, I'm Sravan. This is my submission for the VexarDrive DevOps and Cloud
Infrastructure Engineer assessment. I was given an existing Fleet Ping Service —
a Node.js and Express backend that ingests vehicle location pings and handles
driver login, backed by PostgreSQL. My job was to treat it as a service I now
own and make it production-ready on Azure. Let me walk you through what I found,
what I changed, and why."

## 1. The original problems

[Run: `git log --oneline`]

"Here's the history. I kept my changes as small, reviewable commits. But first,
let's look at the code I inherited."

[Run: `git show b38b522:server.js`]

"This original service had several serious problems. The database credentials
and the JWT signing secret were hardcoded right here in the source. The login
query was built by string concatenation — that's a SQL injection. The admin
endpoint that returns all driver data had no authentication at all. The login
accepted an OTP field but never actually verified it — a complete auth bypass.
And a brand-new database connection was opened and closed on every single
request, which would collapse under real ping traffic."

[Run: `git show b38b522:Dockerfile`]

"The container was just as risky — an unpinned 'node latest' base, running as
root, and it even exposed SSH on port 22, which has no business in a container.
And the compose file committed a production-looking database password. So my
priorities were clear: secrets, injection, broken authentication, and
connection handling first."

## 2. The application fixes

[Open the `src/` folder]

"I refactored the single file into small, testable modules. Configuration now
comes entirely from the environment and is validated at startup — nothing is
hardcoded. Every query is parameterised, so the SQL injection is gone. Login is
now a real one-time-password flow: the OTP is hashed, expiring, single-use, and
rate-limited, and it's actually verified before I issue a token. The admin
endpoint now requires a valid token and an admin role. And there's a single
shared connection pool instead of a client per request."

[Run the demo flow: request-otp, grab OTP from logs, login, ping, admin, injection]

"Let me show it running. I request an OTP for a driver... the OTP is logged in
dev mode... I log in with it and get back a JWT... I send an authenticated ping,
which is accepted... but the admin route rejects my driver token with a 403 —
that used to be wide open. And if I try a SQL injection in the phone field, it's
rejected at validation with a 400 and never touches the database."

[Run: `npm test`]

"And the automated tests cover all of this — health checks, the auth flow, the
injection rejection, and the authorization rules."

## 3. Containerization

[Open the Dockerfile]

"The container is now a multi-stage build on a pinned Alpine base. It installs
production dependencies only, runs as a non-root user, uses tini as the init
process so it shuts down gracefully, and has a health check. SSH is gone.
Secrets never enter the image."

## 4. Infrastructure

[Open `terraform/`]

"For infrastructure I used Terraform, organised into reusable modules with
separate dev and prod environments that differ only by sizing. I was asked to
use AKS, so I did — but I kept it cost-efficient on purpose: the free control
plane tier in dev, a single small autoscaling node pool, and an optional cheap
spot pool for bursts. I'm honest in my report that Container Apps would be
cheaper for a single service, and I explain when AKS becomes worth it."

"The database is a managed PostgreSQL Flexible Server, private inside the
virtual network with no public endpoint, with connection pooling, automated
backups, point-in-time recovery, and high availability in production. Secrets
are generated by Terraform and stored in Key Vault, and the pods read them at
runtime using Workload Identity — so there's no secret on disk anywhere."

[Run: `terraform validate` and `helm lint`]

"I don't have a live Azure subscription for this, which the brief allows, so I'm
validating the configuration rather than deploying it."

[Open `docs/architecture.svg`]

"Here's the architecture. Only the ingress is public. Everything else — the
cluster, the database, Key Vault — is private. A ping comes in over HTTPS, hits
the pods, which talk to PostgreSQL over the private network, and fetch their
secrets from Key Vault using their managed identity."

## 5. CI/CD

[Open `.github/workflows/ci.yml` and `cd.yml`]

"The original pipeline deployed straight to production on every push, with no
tests, no scans, and no way back. I replaced it with a proper pipeline: test,
security scan, build, scan the image, push it tagged by commit SHA, deploy to
dev, verify, then pause for a manual approval before production, and roll back
automatically if a deploy fails. Authentication uses OIDC, so there are no
stored cloud credentials."

## 6. Monitoring and close

"For observability there are separate liveness and readiness endpoints,
structured JSON logging with secrets redacted, and alerts on the things that
actually matter — database CPU, storage, and connection saturation."

"To sum up: I fixed the critical security issues first, then rebuilt the
container, the infrastructure, the pipeline, and the database operations around
sound production practices — and I kept everything sized appropriately for a
single service at an early-stage company. The full reasoning, trade-offs, and
what I'd do next are in the technical report. Thanks for watching."
