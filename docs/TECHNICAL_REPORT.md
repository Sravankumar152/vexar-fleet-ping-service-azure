# Fleet Ping Service — Technical Report

**Author:** Sravan Kumar
**Role assessment:** DevOps & Cloud Infrastructure Engineer, VexarDrive Technologies
**Scope:** Take the inherited Fleet Ping Service to a production-ready state on Azure (AKS).

---

## 1. Executive summary

The Fleet Ping Service is a small Node.js/Express + PostgreSQL backend that
ingests vehicle location pings and authenticates drivers. The inherited code was
functional but carried serious production risks: hardcoded credentials, a SQL
injection, an unauthenticated admin endpoint that leaked all driver data, a new
database connection per request, and a container/CI setup that shipped straight
to production with no tests, scans, or rollback.

I addressed the highest-risk items first (secrets, injection, broken auth,
connection handling), then rebuilt the operational surface: a hardened container,
Terraform for a cost-efficient-but-reliable AKS platform, a gated CI/CD pipeline,
private networking with Key Vault + Workload Identity, database migrations and
least-privilege access, and meaningful monitoring. A live Azure deployment was
not performed (the brief does not require one); the IaC is written to be correct
and reviewable.

The guiding principle throughout was the brief's own: *practical engineering
decisions over unnecessary complexity*. Choices are sized for a single service
at an early-stage company, and every non-trivial decision is justified below.

---

## 2. Initial assessment of the repository

The starter repo contained `server.js`, `schema.sql`, a `Dockerfile`,
`docker-compose.yml`, `package.json`, a `README`, and a single GitHub Actions
workflow. Reading it as an inherited production service, I catalogued issues by
risk before changing anything. The code even flags some problems as
"intentional," so the exercise is prioritisation and judgement, not a checklist.

## 3. Issues identified (prioritised)

| # | Severity | Area | Issue |
|---|----------|------|-------|
| 1 | Critical | Secrets | DB credentials + JWT secret hardcoded in `server.js`; prod DB password committed in `docker-compose.yml`; static `ACR_PASSWORD` in CI. |
| 2 | Critical | Injection | `/api/auth/login` built SQL by string interpolation of `phone` — classic SQL injection. |
| 3 | Critical | AuthZ | `/api/admin/drivers` had no authentication and returned all driver rows. |
| 4 | Critical | AuthN | Login accepted an `otp` field but never verified it — full auth bypass. |
| 5 | High | Reliability | A new `pg.Client` was opened/closed on **every** request — connection storms under bursty ping load. |
| 6 | High | Container | `node:latest` (unpinned), ran as root, `EXPOSE 22`, installed dev deps, no healthcheck, no signal handling. |
| 7 | High | CI/CD | Every push to `main` deployed to prod with no test/scan/approval/rollback; mutable `:latest` tag. |
| 8 | Medium | Data | No indexes on the append-heavy `fleet_pings`; `SERIAL`/`TIMESTAMP` (no tz); nullable lat/lng. |
| 9 | Medium | Networking | Postgres bound to `0.0.0.0`; no network isolation. |
| 10 | Medium | Observability | Unstructured `console.error`; no health/readiness endpoints; no metrics/alerts. |

## 4. Changes made and why

**Secrets removed from source (issue 1).** All configuration now comes from the
environment through a validated `src/config.js` that fails fast in production if
a required secret is missing. In Azure, secrets are generated by Terraform,
stored in Key Vault, and delivered to pods at runtime via the CSI driver — never
in git or images. The CI workflow uses OIDC federation instead of a stored
registry password.

**SQL injection fixed (issue 2).** Every query is parameterised. The login query
is now `WHERE phone = $1`. A test asserts that an injection payload in `phone` is
rejected at validation and never reaches the database.

**Authentication and authorization (issues 3, 4).** Login is a real two-step OTP
flow: `request-otp` issues a random, salted-scrypt-hashed, expiring, single-use,
attempt-capped OTP; `login` verifies it (constant-time) before signing a JWT.
The admin endpoint now requires a valid JWT **and** the `admin` role, and
paginates. The ingestion endpoint is authenticated and validated.

**Connection pooling (issue 5).** A single shared `pg.Pool` replaces per-request
clients, with connect/idle/statement timeouts and pool-level error handling. In
Azure it sits behind PostgreSQL's built-in PgBouncer.

**Container hardening (issue 6).** Multi-stage build on a pinned
`node:20.17-alpine`, production-only deps via `npm ci --omit=dev`, non-root
`node` user, `tini` as PID 1 for signal forwarding and zombie reaping, a
`HEALTHCHECK`, and `EXPOSE 22` removed. `.dockerignore` keeps secrets, tests and
IaC out of the image.

**CI/CD rebuilt (issue 7).** Two workflows implement
Test → Security Scan → Build → Containerize → Deploy → Verify with dev/prod
environments, a manual prod approval gate, image promotion by immutable SHA, and
automatic Helm rollback on failure. Details in §8.

**Database (issue 8).** Versioned migrations (transactional runner), indexes for
the hot read paths, `timestamptz`, NOT NULL constraints, an OTP table, and a
least-privilege `fleet_app` role.

**Networking, observability, hygiene (issues 9–11).** Private VNet with a
VNet-integrated database (no public endpoint), structured pino logging with
secret redaction, `/healthz` + `/readyz`, metric alerts, and standard repo
hygiene files, validation, and tests.

## 5. What I deliberately did *not* change (and why)

- **Framework/runtime.** Express + `pg` are appropriate; rewriting in another
  stack would add risk with no benefit for a service this size.
- **A separate device-identity system for pings.** I authenticated ingestion
  with the existing JWT rather than designing a full device-provisioning/mTLS
  scheme — correct long-term, but out of proportion to the assessment. Noted as
  a next step.
- **Managed Postgres over self-hosting.** I did not containerise Postgres for
  production; a managed Flexible Server is the right call for backups/HA/patching.
- **Multi-region / active-active.** Over-engineered for the current stage; the
  scaling path is described instead (§13).
- **A service mesh, API gateway, or event bus.** No current requirement justifies
  the operational cost.

## 6. Architecture decisions

**Compute — AKS, kept cost-efficient.** Azure Container Apps would be the
lowest-effort choice for one HTTP service and I would normally recommend it. AKS
was chosen (per requirement) and made cost-efficient deliberately: Free
control-plane tier in dev / Standard (SLA) in prod, a single small autoscaling
node pool (`Standard_B2s` burstable in dev), Azure CNI Overlay to avoid IP
sprawl, an optional Spot pool for cheap burst, and ephemeral-friendly settings.
The honest trade-off: AKS has a higher operational and cost floor than Container
Apps, and that flexibility is only worth it if VexarDrive expects more services,
custom networking, or portability. I would revisit this decision with the team.

**Database — Azure Database for PostgreSQL, Flexible Server.** Managed backups,
PITR, HA, and patching; VNet-integrated for private access; built-in PgBouncer
for connection pooling under bursty load.

**Secrets — generated by Terraform, stored in Key Vault, delivered by CSI +
Workload Identity.** No secret is committed or baked into an image; pods hold no
long-lived credential.

**Environments — separate dev/prod roots and state**, differing only by sizing
toggles, so a new environment is a copy-paste and blast radius is contained.

## 7. Security approach

Defence in depth across identity, network, and data:

- **Identity:** pods use Workload Identity (federated OIDC, no client secret);
  CI uses GitHub OIDC (no stored cloud credential); Key Vault and AKS use Azure
  RBAC; the app DB role is least-privilege (DML only, no DDL).
- **Network boundaries:** only the AKS ingress is public (HTTPS/TLS). The AKS API
  server (prod), PostgreSQL, Key Vault and ACR are private (VNet integration /
  private endpoints). The database has **no** public endpoint and enforces TLS.
- **Application:** parameterised queries, input validation (zod), OTP hashing +
  rate limiting, `helmet` headers, bounded request bodies, generic error
  responses (no stack leakage), JWT with expiry and role checks.
- **Supply chain:** gitleaks (secrets), `npm audit`, Trivy (deps + IaC misconfig
  + image), Dependabot updates, images scanned before push.

No sensitive information is committed to the repository or included in container
images.

## 8. Deployment strategy (CI/CD)

`ci.yml` gates pull requests (test, scan, build-without-push, Helm lint).
`cd.yml` runs on merge to `main`:

1. **Test & scan** — jest, lint, gitleaks, `npm audit`.
2. **Build & scan image** — Buildx build, Trivy scan **before** push, push to
   ACR tagged with the immutable git SHA (never `latest`).
3. **Deploy dev** — Helm to the dev AKS; verify via `rollout status` + an
   in-cluster `/readyz` smoke test.
4. **Approval gate** — the `prod` GitHub Environment requires a reviewer.
5. **Deploy prod** — the same image is promoted by digest (`az acr import`), then
   Helm-deployed and verified.
6. **Rollback** — any failed deploy triggers `helm rollback` to the last good
   revision; immutable SHAs make rollback deterministic.

Environment-specific configuration is non-secret Helm values per environment;
secret values are pulled from Key Vault at runtime. Auth is OIDC throughout.

## 9. Database strategy

- **Backups / PITR:** automated backups with 7-day (dev) / 35-day (prod)
  retention enabling point-in-time recovery; geo-redundant backups in prod.
- **HA:** zone-redundant high availability in prod (a hot standby); single
  instance in dev for cost.
- **Connections:** app-side `pg.Pool` plus server-side **PgBouncer** to absorb
  bursty ping traffic without exhausting backend connections.
- **Access / least privilege:** app connects as `fleet_app` (DML only) — never
  the admin login; the admin credential is used only for provisioning/migrations
  and is Key Vault-stored.
- **Migrations:** versioned SQL applied transactionally by `scripts/migrate.js`,
  tracked in `schema_migrations`; run as a pre-deploy Kubernetes Job in prod.
- **Indexes:** `(vehicle_id, ts DESC)`, `(ts DESC)`, `(created_at)` for the
  latest-per-vehicle and time-range queries on the append-heavy table.

## 10. Monitoring & observability

- **Endpoints:** `/healthz` (liveness, no DB dependency so a DB blip doesn't
  restart healthy pods) and `/readyz` (readiness, checks the DB so unready pods
  leave the load balancer).
- **Logs:** structured JSON (pino), one object per line for Log Analytics, with
  authorization/password/OTP/token fields redacted; per-request correlation.
- **Metrics & alerts (what / trigger / why):**
  - *PostgreSQL CPU > 80% for 15m* — ingestion latency/timeout risk; the DB is
    the most likely bottleneck.
  - *PostgreSQL storage > 85%* — writes fail at 100%; needs lead time to grow.
  - *Active connections near the limit* — pool/PgBouncer pressure before it
    becomes user-visible.
  - *(Recommended next)* ingress 5xx rate, p95 request latency, and pod
    restart/CrashLoop and HPA-at-max — the app-side SLIs.
- **Platform:** Container Insights ships pod stdout/metrics to Log Analytics; a
  daily ingestion cap controls cost in non-prod.

## 11. Cost considerations

The footprint is deliberately small: Free AKS tier and Burstable DB in dev, a
single autoscaling node pool, Basic ACR, capped Log Analytics ingestion, and an
optional Spot pool for cheap burst. Prod spends where reliability demands it —
Standard AKS SLA, HA + geo-redundant database, private endpoints — and nowhere
else. The largest cost levers are AKS node count and the database tier/HA;
scale-to-need via the cluster autoscaler and HPA keeps idle spend low. The main
cost caveat is that AKS itself costs more than Container Apps would for this
workload (§6).

## 12. Scalability considerations

Ingestion is horizontally scalable: stateless pods behind the HPA, the cluster
autoscaler adding nodes, and PgBouncer shielding the database. The first limit
reached will be database write throughput on `fleet_pings`.

## 13. How the data approach evolves with fleet growth

- **Now (small fleet):** single Flexible Server, indexed table, PgBouncer.
- **Growing:** scale the DB tier up; offload heavy dashboard/analytics reads to
  a **read replica**; tighten indexes/queries.
- **High volume:** **partition `fleet_pings` by time** (monthly/weekly) so writes
  hit a small active partition and old data is cheap to archive/drop; add a
  retention/rollup job; consider a time-series extension (TimescaleDB) or an
  append-optimised store, and a buffer (Event Hubs) in front of ingestion to
  decouple spikes from database writes.

## 14. Assumptions & constraints

- Traffic is write-heavy pings plus occasional auth and admin reads.
- OTP **delivery** (SMS) is out of scope and stubbed (logged in dev); the
  issuance/verification mechanics are implemented.
- A single Azure region is sufficient at this stage.
- No live Azure subscription was used; IaC is validated by structure/review, not
  applied (the brief permits this).
- `azurerm` provider `~> 3.116` is pinned for stability.

## 15. Known limitations

- **Not deployed live**, so `terraform plan/apply` and `helm install` have not
  been run against real Azure; `terraform validate` and `helm lint` should be run
  locally before any deployment.
- **`package-lock.json` must be generated and committed** (`npm install` once)
  for `npm ci` in the Dockerfile/CI; it was not generated here because the build
  sandbox had no package-registry access.
- Ingestion uses the driver JWT rather than a dedicated device identity.
- Alerting covers the essentials; full SLO/error-budget dashboards are a next
  step.
- A shared vs per-environment container registry is a trade-off; the pipeline
  promotes by digest either way (documented in the CI/CD README).

## 16. What I would do next (with more time)

1. Generate/commit the lockfile and run the pipeline end-to-end against a real
   subscription.
2. Add app-level metrics (Prometheus/OpenTelemetry) and SLO dashboards + alerts
   on 5xx rate and p95 latency.
3. Introduce a device-identity/token model for ping ingestion.
4. Partition `fleet_pings` and add a retention/rollup job.
5. Add `terraform validate`/`tflint`/`checkov` and `helm lint`/`kubeconform` as
   CI jobs; add policy (OPA/Gatekeeper or Azure Policy) on the cluster.
6. Add PagerDuty/Teams routing on the action group and on-call runbooks.
