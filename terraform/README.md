# Fleet Ping Service — Azure Infrastructure (Terraform)

Infrastructure-as-Code for running the Fleet Ping Service on Azure using
**AKS** for compute and **Azure Database for PostgreSQL – Flexible Server**
for storage, with Key Vault, ACR, private networking and monitoring.

The design goal is a **cost-efficient but production-reliable** footprint:
small autoscaling node pools, Burstable database tiers in non-prod, private
networking, workload identity (no secrets on disk), and Azure-native
monitoring. Every choice is sized for a single service at an early-stage
company — not for maximum feature coverage.

> A live Azure deployment is **not** part of this assessment. This code is
> written to be correct and reviewable; `terraform init/plan` require Azure
> credentials and a remote state backend, described below.

## Why AKS (and how we keep it cheap)

Azure Container Apps would be the lowest-effort choice for a single HTTP
service. AKS was chosen deliberately (per requirement) and is kept
cost-efficient by:

- **Free control-plane tier** in dev, **Standard** (financially-backed SLA)
  only in prod.
- A **single small autoscaling system node pool** (`Standard_B2s` burstable
  in dev), scaling to zero-idle headroom via the cluster autoscaler.
- **Azure CNI Overlay** networking — no large subnet / IP exhaustion, fewer
  moving parts than a separate ingress VM tier.
- **Optional Spot user node pool** (disabled by default) for burst / batch
  capacity at ~1/5 the price.
- **Workload Identity** instead of secrets, so there is no secret-store
  sidecar cost or secret sprawl.

The trade-offs vs Container Apps are documented in the technical report.

## Layout

```
terraform/
├── modules/
│   ├── network/       VNet, subnets, NSGs, private DNS zones
│   ├── identity/      App workload identity + federated credential + RBAC
│   ├── acr/           Azure Container Registry
│   ├── keyvault/      Key Vault (RBAC-authorized) + optional private endpoint
│   ├── postgres/      PostgreSQL Flexible Server (private) + DB + secrets
│   ├── aks/           AKS cluster (workload identity, CSI, Container Insights)
│   └── monitoring/    Log Analytics, action group, metric/log alerts
└── envs/
    ├── dev/           Cheap, single-AZ, Free AKS tier, public-restricted KV
    └── prod/          HA database, Standard AKS tier, private endpoints
```

Modules are environment-agnostic; all sizing/toggles come from the `envs/*`
roots. Another engineer can stand up a new environment by copying an env
folder and editing `terraform.tfvars`.

## Prerequisites

- Terraform >= 1.5
- An Azure subscription and `az login` (or a service principal / OIDC in CI)
- A **remote state backend** — an Azure Storage Account + container. Create it
  once, out of band, then fill `backend.tf` (see `envs/dev/backend.tf`).

## Usage

```bash
cd terraform/envs/dev
cp terraform.tfvars.example terraform.tfvars   # edit values (no secrets!)
export ARM_SUBSCRIPTION_ID=<your-sub-id>
terraform init
terraform plan
terraform apply
```

## Secrets

No plaintext secrets live in this repo. The PostgreSQL admin password is
**generated by Terraform** (`random_password`) and written straight into Key
Vault; the application reads it at runtime through Workload Identity + the
Key Vault CSI driver. The only place the generated value exists is Terraform
**remote state**, which must be stored in an access-controlled, encrypted
backend. This trade-off is discussed in the report.
```
